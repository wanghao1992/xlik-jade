# 位移/高度占用调度（待释放表）设计方案

## 一、目标与结论

新增一个**按英雄维度的位移调度器**（下文称 `moveFlow`），把下面这些会改写英雄坐标或凌空高度的系统统一纳入仲裁：

- 天赋：天降斩（多段 `ability.leap`）、御剑飞行（每帧 `SetUnitX/Y` + 升空 Buff）。
- 随机事件：雷霆扑杀、天降巨剑、坐骑冲锋/野蛮冲撞、凌波微步。
- 技能：传送。

**不纳入**：剑阵（只跟随英雄坐标、不改本体）、分身诱饵（不移动英雄本体）、对敌人的击飞/击退（`ability.crackFly` 作用于目标，不占用英雄）。

采用用户确认的**混合策略**：

- **短爆发（burst）**：天降斩、传送。可以打断长状态，长状态被挂起（`suspended`），爆发结束后自动恢复。
- **长状态（state）**：御剑飞行、雷霆扑杀、天降巨剑、坐骑冲锋/野蛮冲撞、凌波微步。长状态之间不抢占，进入待释放表按优先级排队。
- **等待超时丢弃**：每个请求带 TTL；等待超过 TTL 的请求不再释放，避免表无限堆积、也避免迟到的无意义触发。
- **冷却只在真正启动时消耗**：排队期间不占冷却；被 TTL 丢弃也不进冷却。

核心防堆积手段（解决"表过长"）：

1. 待释放表是**按来源 key 索引的 map**，同一来源永远只有 1 个槽位，表长度上限 = 来源数量（当前 8 个），不会随触发次数增长。
2. 同一 key 重复触发只刷新参数、不新增条目。
3. TTL 过期在每次释放/pump 时清理。
4. 每个活动条目带 `maxDuration` 看门狗，超时强制释放，防止回调丢失导致永久占用。
5. 英雄死亡/销毁立即清空活动与待释放表。
6. 爆发的最大等待 = 当前爆发剩余时长 + 1 秒，不会因为"前面的长事件"等几十秒。

### 现有冲突的具体表现

1. 同一次普攻同时触发天降斩与御剑：两边各自启动，天降斩的 `leap` 与御剑的 `SetUnitX/Y` / `flyHeight` 同时写位置与高度。
2. 野蛮冲撞期间触发天降斩：`ability.leap` 会顶掉冲锋当前那一段；冲锋 tick 下一帧又发起新冲锋，形成来回抢占。
3. 随机事件之间：`prepareMoveEvent` 直接终止旧事件，30 秒事件被反复吃掉。
4. 任何一方回调丢失/异常，`_moveStop`、`_talentLeapRunning` 等锁定字段可能残留，后续全部卡死。

## 三、调度器设计

### 3.1 数据模型

每个英雄挂一个调度器：

```lua
hero._moveArbiter = {
    state = nil,        -- 当前长状态条目（见下）
    stateSuspended = false, -- 长状态是否被爆发挂起
    burst = nil,        -- 当前爆发条目
    pending = {},       -- key -> 请求条目（按来源去重，map 不是数组）
    pendingCount = 0,
    serial = 0,         -- 防止旧看门狗误清新条目
}
```

条目结构：

```lua
{
    key = "talent_leap",   -- 唯一来源 key
    label = "天降斩",       -- 调试/日志用
    kind = "burst",        -- "burst" | "state"
    priority = 600,        -- 待释放表排序用（大者优先）
    ttl = 2,               -- 排队有效期（秒）
    maxDuration = 12,      -- 看门狗上限（秒）
    at = 12.34,            -- 入队时间
    expiresAt = 14.34,     -- 过期时间（计算后的有效 TTL）
    start = function() ... return true end, -- 真正启动；返回 false 表示没启动
    cancel = function() ... end,            -- 被强制终止时清理
    suspend = function() ... end,           -- 长状态被爆发挂起时调用（可选）
    onResume = function() ... end,          -- 挂起结束恢复时调用（可选）
}
```

### 3.2 对外 API

新增全局模块 `moveFlow`（文件见第四节）：

| API | 说明 |
| --- | --- |
| `moveFlow.request(hero, req)` | 申请占用。返回 `"started" / "queued" / "merged" / "dropped"` |
| `moveFlow.beginEvent(hero, name, retryFn)` | 随机事件专用包装（见 3.5），返回 `true` 表示本次调用应继续执行事件体 |
| `moveFlow.release(hero, key)` | 释放指定来源；幂等，不存在时忽略 |
| `moveFlow.isActive(hero, key)` | 该来源是否正在运行 |
| `moveFlow.isBusy(hero)` | 是否已有 state/burst 占用 |
| `moveFlow.isSuspended(hero)` | 当前长状态是否被爆发挂起（长事件循环用它跳过移动） |
| `moveFlow.clear(hero, reason)` | 清空活动与待释放表（死亡/测试/异常） |
| `moveFlow.debug(hero)` | 返回可读的活动 + 待释放表文本，供 `-tq` 使用 |

`request` 的 `req.kind` 缺省为 `"state"`；`req.force = true` 表示玩家主动技能（传送）强制抢占。

### 3.3 决策矩阵

| 当前占用 | 新请求 | 处理 |
| --- | --- | --- |
| 空闲 | 任意 | 立即启动 |
| 长状态 | 爆发 | 标记 `stateSuspended = true`，调用旧条目 `suspend()`（默认 `ability.moveStop(hero)`），启动爆发；爆发结束后 `onResume()` 并解除挂起 |
| 爆发 | 爆发 | 入待释放表；有效 TTL = 当前爆发剩余时长 + 1 秒 |
| 爆发 | 长状态 | 入待释放表；有效 TTL = 当前爆发剩余时长 + 1 秒 |
| 长状态 | 长状态（不同 key） | 入待释放表，TTL 取请求值（默认 8 秒） |
| 长状态/爆发 | 同 key | 天赋：只刷新参数与 TTL，不新增条目，返回 `merged`；随机事件：由 3.5 的 `beginEvent` 短路进事件体，走原有"延长时长"分支 |
| 任意 | `force=true` 的爆发（传送） | 取消当前爆发（若有）、挂起长状态、立即启动传送；待释放表保留 |
| 任意 | 英雄已死/销毁 | 直接 `dropped` |

释放时 `pump` 的顺序：

1. 英雄已死/销毁 → `clear`。
2. 若仍有爆发 → 等待（爆发结束后会再次 pump）。
3. 若存在被挂起的长状态 → 先解除挂起并调用 `onResume`，**恢复原长状态**，本次不再启动新条目（保持"一个结束再开始另一个"的直觉）。
4. 若存在运行中的长状态 → 等待其释放。
5. 清理已过期条目（`now >= expiresAt`）。
6. 从待释放表取 `priority` 最大者；同优先级取 `at` 最早者；启动它。
7. 若 `start()` 返回 `false`，立即释放该条目并重复第 5 步（最多循环 8 次，防止死循环）。

### 3.4 默认参数

| 来源 key | kind | priority | ttl | maxDuration |
| --- | --- | --- | --- | --- |
| `teleport` | burst（force） | 1000 | 1 | 2 |
| `talent_leap`（天降斩） | burst | 600 | 2 | 15 |
| `talent_ride`（御剑飞行） | state | 500 | 8 | 御剑持续 + 8 |
| `event_sword`（天降巨剑） | state | 400 | 8 | 45 |
| `event_mount`（冲锋/野蛮冲撞） | state | 300 | 8 | 45 |
| `event_serpentine`（凌波微步） | state | 200 | 8 | 45 |
| `event_harvest`（雷霆扑杀） | state | 100 | 8 | 45 |

- `ttl` 可在单次请求中覆盖（例如未来想给御剑更长的等待窗口，只改调用处）。
- 待释放表硬上限 `MAX_PENDING = 6`：插入前若已满，先淘汰 `priority` 最低、`at` 最早的一条。

### 3.5 随机事件的重入包装

随机事件是"整段函数体"式的启动，不能在函数体中间挂起，所以用重入包装：

```lua
function randomEvent.startMountCharge(pla, hero, duration, tag, savage, retry)
    -- 参数校验
    if (true ~= retry and false == moveFlow.beginEvent(hero, "mount", function()
        return randomEvent.startMountCharge(pla, hero, duration, tag, savage, true)
    end)) then
        return
    end
    -- 原有函数体（此处才产生 Buff / 坐骑 / 定时器等副作用）
end
```

`beginEvent` 内部：

- 若调度器记录 `_startingKey == "event_mount"`（调度器回调进来的重入），或该 key 已经是当前 `state`/`burst`，直接返回 `true`：
  - 重入场景继续执行事件体；
  - 同事件重复触发场景继续执行到 `prepareMoveEvent`，由它走"延长时长"分支后返回，**不会重启事件**。
- 否则（该 key 空闲或在待释放表中）调用 `request`，`start` 回调里设置 `_startingKey`、调用 `retryFn()`、再清空；返回 `false`，让原始调用结束。
- 这样既不会重复执行事件体，也能把入口包在**任何副作用之前**，同时保留同事件延长的原有语义。

四种事件（harvest / sword / mount / serpentine）都按此处理；调用签名追加可选 `retry` 参数，外部调用（事件数据表、奥义）不受影响。


`moveFlow.debug` 输出格式：`active=事件名(kind,已运行X秒) suspended=是/否 pending=[key 剩余TTL, ...]`。

## 五、假设与决策

1. **纳入范围**：只纳入会改英雄坐标/高度的系统；剑阵、分身诱饵、对敌击飞不参与（按用户选择）。
2. **长状态之间排队、不抢占**；爆发可以挂起长状态并在结束后恢复（按用户选择）。
3. **超时丢弃**：天赋默认 2 秒/8 秒、随机事件 8 秒；被丢弃不消耗冷却，下次普攻可再触发（按用户选择）。
4. **冷却口径**：`_talentLeapLock` / `_talentSwordRideLock` 由 `start` 回调写入，保证"真正开始才进冷却"。
5. **御剑被挂起时冻结持续时间**：`state.elapsed` 暂停累加，避免爆发期间自然到期与高度还原冲突；代价是御剑总占用时间可能延长爆发时长。
6. **随机事件被挂起不延长自身 30 秒**：事件自身 `expireAt` 继续走，挂起期间相当于丢失几秒；30 秒事件被 6 秒爆发打断的影响可接受，且避免为每个事件改结束定时器。
7. **随机事件排队超过 TTL 就丢弃**：玩家已接受事件但未能启动时静默丢弃，不产生残留 Buff/坐骑；若后续希望给"已接受"事件更长等待，只需调大该事件请求的 `ttl`。
8. **看门狗兜底**：任何系统漏调 `release` 都会在 `maxDuration` 后强制释放，避免永久卡死。
9. **不修改库层** `ability.leap` / `ability.serpentine`：仲裁在业务层完成；库层仍保留"后到顶掉"作为最后防线，但正常流程不会再让两个位移同时存在。
10. **新模块放 `globals/setup/`**：setup 先于 tpl 加载，且构建自动打包，无需 `require`；运行时调用不依赖具体文件加载先后。
